## 2. Adversarial Verification of Candidate Inference Models (as of 2026-11-22)

An initial assumption of **"20B–70B class models" contradicts all four candidate models below.** All four are ultra-large Mixture-of-Experts (MoE) architectures (**320B to ~2.8T total parameters**, requiring **~320 GB to ~1,561 GB** for weights alone), which cannot run on 1–2 GPUs and instead require multi-GPU nodes (such as 8x H100 / 8x H200 / 8x B300). Furthermore, **open-weight models must not be equated with fully open-source (OSI-compliant with public training data/recipes) software.**

| Candidate Model | Existence & Official Repository | Total / Active Parameters | Weight Release & License Category | vLLM Support & Caveats | Estimated Weight Memory (Excluding KV Cache) | Fit vs. 20B–70B Assumption |
|---|---|---|---|---|---|---|
| **GLM-5.3** | Exists: `zai-org/GLM-5.3` | ~**744B–753B** total / **40B** active (MoE) | **Open-weight (modified MIT license):** Includes a clause requiring Z.AI safety review for commercial MaaS providers with >$10B annual revenue (not pure OSI OSS). | vLLM / SGLang supported. Defaults to `reasoning_effort: max` and `clear_thinking: false`, requiring explicit vLLM deployment flags and request-level control. | ~**744–756 GB** in FP8 (e.g., 8x H200 node class) | **Mismatch** (40B active, but 744B total requires 750 GB+ VRAM) |
| **GLM-5.3-Flash** | Exists: `zai-org/GLM-5.3-Flash` | **320B** total / **18B** active (hybrid MoE) | **Open-weight (MIT License):** Weights and code are MIT, though training data is closed (distinguish from full OSS). | vLLM supported. Depends on `trust_remote_code=True` and custom processor/encoding. | ~**1,561 GB** even at 4-bit MXFP4 (dedicated 8x B300 / TP=8 node class) | **Major mismatch** (2.8T-class, >1.5 TB VRAM required) |

### Architectural Implications
1. If your air-gapped GPU budget is sized for 20B–70B models (e.g., 1–4x A100/H100 80 GB), none of the four models above can be deployed as-is. Either select a 20B–70B class MIT/Apache-2.0 open-weight model, provision 8x H200 / 8x B300 inference hardware, or route `grafana-llm-app` to an internet-hosted OpenAI-compatible API where permitted by policy.
2. This plugin **never hardcodes any model name or parameter scale**. Inference targets are completely swappable through `grafana-llm-app`'s logical model tiers (`base` / `large`).
3. `reasoningEffort` defaults to `""` (omitted) so standard non-reasoning models (`gpt-4o`, `gpt-4.1`, Llama, `deepseek-chat`) do not fail with HTTP `400`. For reasoning models such as `o3`, `gpt-5`, `GLM-5.3`, or `GLM-5.3-Flash`, explicitly set `reasoningEffort` to `"low"` in App Config alongside `maxOutputTokens` (default `2048`), and the Go backend treats `finish_reason == "length"` as an explicit `ErrOutputTruncated` failure.

## 3. Protocol Constraints Verified via `grafana-llm-app` Contract & Live Container Tests

Verified directly from `pkg/llm/contract_test.go`, upstream source inspection, and live container wire captures via `make verify-llm-protocol` against **real `grafana-llm-app v1.2.0` (`Grafana 13.3.1`)** and **real `grafana-llm-app v1.0.8` (`Grafana 12.4.15`)**:

1. **Logical Model Routing:** `grafana-llm-app` accepts only `"base"` or `"large"` in the request `model` field (arbitrary model names return HTTP `400`) and translates them to the actual served model name via `ModelSettings.Mapping` (verified live on both `v1.2.0` and `v1.0.8`).
2. **Structured Output (`response_format`) Pass-Through & Version Differences:**
   - `response_format: { type: "json_schema", json_schema: { name, schema, strict: false } }` passes through both `grafana-llm-app v1.2.0` and `v1.0.8` to upstream OpenAI-compatible endpoints (including `dashboard_ir`, `dashboard_patch`, and string enums such as `datasourceRef: ["selected_prometheus"]`).
   - Internally, `grafana-llm-app` unmarshals the schema into `go-openai/jsonschema.Definition`, whose `Enum` field is `[]string`. **Any numeric `enum` (e.g., `[0, 1]`) causes `json.Unmarshal` to fail with HTTP `400`.** Both canonical schemas use string-only enums, express numeric bounds via `minimum`/`maximum`, and are continuously verified by `scripts/verify-schema-sync.mjs`.
   - **Empirical wire difference (`v1.2.0` vs. `v1.0.8`):** Live container wire captures confirmed that `grafana-llm-app v1.2.0` (built with `go-openai v1.43.0`) **preserves** `minLength`, `maxLength`, `minimum`, and `maximum` in `response_format.json_schema.schema`, whereas `grafana-llm-app v1.0.8` (Grafana 12.4.x) **drops** `minLength`, `maxLength`, `minimum`, `maximum`, and `pattern` during relay. Neither version can represent nullable union types (`["string", "null"]`) required by OpenAI `strict: true`. Therefore, `Strict: false` is retained and the Go backend deterministically re-enforces all length, numeric, regex, PromQL AST, and catalog rules across both versions and in `json_object` mode.
3. **Provider Compatibility Modes (`json_object`, `max_tokens`, `reasoning_effort`):**
   - Verified on real `v1.2.0` and `v1.0.8` containers: `structuredOutputMode=json_object` with `tokenLimitField=max_tokens` (`deepseek` preset) relays `response_format.type="json_object"`, `max_tokens`, omits `max_completion_tokens`, and embeds the canonical JSON Schema in the system message; `reasoningEffort="low"` (`openai-o3` preset) relays `reasoning_effort="low"` while omitting `temperature`.
4. **Non-Pass-Through of `extra_body` / `chat_template_kwargs`:**
   - Fields outside `go-openai.ChatCompletionRequest` (such as `structured_outputs` or `chat_template_kwargs: {"clear_thinking": true}`) are stripped by `grafana-llm-app`. Engine-specific template defaults must therefore be pinned in vLLM startup flags.
5. **Error, Timeout & Cancellation Propagation:**
   - `grafana-llm-app`'s `openai_provider.go` uses a fixed `2 * time.Minute` HTTP client timeout. The Go backend applies shorter `llmTimeoutSeconds` (default `45s`) and `jobDeadlineSeconds` (default `90s`) via `context.WithTimeout` so cancellations propagate through Grafana -> `grafana-llm-app` -> upstream LLM.
   - Transport retries (max 1 retry for transient network failures, HTTP `502`/`503`/`504`, or `grafana-llm-app` HTTP `500` responses wrapping upstream `502`/`503`/`504`/`520`/`522`/`524`) and `finish_reason == "length"` (`ErrOutputTruncated`) detection were verified live against both `v1.2.0` and `v1.0.8` containers, strictly separated from semantic syntax repairs (max 2 per job).
